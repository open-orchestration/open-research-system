This finding grounds three official Model Context Protocol (MCP) specification pages, version `2025-06-18`: the **Tools** server page [c93368f06], the **Prompts** server page [cc324bc4a], and the **Security Best Practices** page [cf13e1cfc]. It supplies the exact message shapes for the two model- and user-facing primitives and the named threat/mitigation pairs an HTTP-exposed server must implement. It complements promoted finding `d3c246500`, which already grounds MCP architecture, the two transports, the OAuth 2.1 authorization model, and the Resources primitive; this finding does not restate that material — it adds the Tools and Prompts wire contracts and the Security Best Practices page, neither of which `d3c246500` covered in detail.

## Tools

Tools in MCP are **model-controlled**: the language model can discover and invoke tools automatically [c93368f06]. Because the model drives invocation, the spec sets a human-in-the-loop expectation — applications SHOULD provide UI that makes clear which tools are exposed to the model, insert clear visual indicators when tools are invoked, and present confirmation prompts to the user so a human is in the loop [c93368f06].

A server that supports tools **MUST** declare the `tools` capability, optionally with `listChanged` set, where `listChanged` indicates whether the server will emit notifications when the list of available tools changes [c93368f06]. Discovery uses a `tools/list` request, which supports pagination via an optional `cursor` param and returns a `tools` array [c93368f06]. Invocation uses a `tools/call` request whose `params` carry `name` (matching a discovered tool) and `arguments` [c93368f06].

A tool definition includes `name` (unique identifier), an optional `title` (human-readable display name), a `description`, an `inputSchema` (a JSON Schema defining expected parameters), an optional `outputSchema` (a JSON Schema defining expected output structure), and optional `annotations` describing tool behavior [c93368f06]. For trust and safety, clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers [c93368f06].

The `tools/call` result returns unstructured content in a `content` array — which can contain multiple items of different types (text, image, audio, resource links, embedded resources) — together with an `isError` flag [c93368f06]. Results may also carry **structured** content as a JSON object in the `structuredContent` field; for backwards compatibility a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block [c93368f06]. When a tool provides an `outputSchema`, servers **MUST** provide structured results that conform to it and clients **SHOULD** validate structured results against it [c93368f06]. When the tool list changes, a server that declared `listChanged` **SHOULD** send a `notifications/tools/list_changed` notification [c93368f06].

## Prompts

Prompts are **user-controlled**: they are exposed from servers to clients with the intention that the user can explicitly select them, typically through user-initiated commands such as slash commands, though the protocol mandates no specific interaction model [cc324bc4a]. A server that supports prompts **MUST** declare the `prompts` capability during initialization, optionally with `listChanged` [cc324bc4a].

Discovery uses a `prompts/list` request; retrieval uses a `prompts/get` request whose `params` carry `name` and an `arguments` object [cc324bc4a]. A prompt definition includes `name` (unique identifier), an optional `title`, an optional `description`, and an optional `arguments` list for customization [cc324bc4a]. Prompt arguments may be auto-completed through the completion API [cc324bc4a]. A `prompts/get` response returns a `description` and a `messages` list of **PromptMessage** objects; each PromptMessage carries a `role` (either "user" or "assistant") and `content` (text, image, audio, or embedded-resource content) [cc324bc4a]. When the prompt list changes, a server that declared `listChanged` **SHOULD** send a `notifications/prompts/list_changed` notification [cc324bc4a].

## Security Best Practices

**Confused deputy.** Attackers can exploit MCP proxy servers that connect to third-party APIs, creating confused-deputy vulnerabilities: a malicious client can obtain authorization codes without proper user consent by exploiting the combination of static client IDs, dynamic client registration, and consent cookies [cf13e1cfc]. The mitigation is per-client consent: to prevent confused-deputy attacks, MCP proxy servers **MUST** implement per-client consent and proper security controls [cf13e1cfc]. Specifically, proxy servers **MUST** maintain a registry of approved `client_id` values per user, check that registry **before** initiating the third-party authorization flow, and store consent decisions securely [cf13e1cfc]. The consent cookie or session carrying the OAuth `state` value **MUST NOT** be set until after the user has approved the consent screen at the MCP server's authorization endpoint [cf13e1cfc].

**Token passthrough.** "Token passthrough" is an anti-pattern where an MCP server accepts tokens from an MCP client without validating that the tokens were properly issued *to the MCP server* and passes them through to the downstream API [cf13e1cfc]. The spec states this is explicitly forbidden in the authorization specification because it circumvents security controls such as rate limiting, request validation, and traffic monitoring that depend on the token audience or other credential constraints [cf13e1cfc]. The remedy is audience validation: the server must validate that an inbound token was issued to it before honoring the request [cf13e1cfc].

**Session hijacking.** Session hijacking is an attack vector where a client is given a session ID by the server and an unauthorized party obtains and uses that same ID to impersonate the original client and perform unauthorized actions [cf13e1cfc]. As mitigations: MCP servers that implement authorization **MUST** verify all inbound requests; MCP servers **MUST NOT** use sessions for authentication; and MCP servers **MUST** use secure, non-deterministic session IDs, with generated IDs (e.g. UUIDs) that **SHOULD** use secure random number generators [cf13e1cfc]. Servers **SHOULD** bind session IDs to user-specific information, combining the session ID with information unique to the authorized user (e.g. an internal user ID) using a key format like `<user_id>:<session_id>`, so that even a guessed session ID cannot impersonate another user [cf13e1cfc].

## Synthesis

These pages complete the MCP picture for the engine. **Tools** are the engine's search and extraction actions: model-controlled invocations carrying a JSON Schema `inputSchema`, returning `content` plus an `isError` flag, and — because the model decides to call them — requiring the spec's human-in-the-loop consent posture [c93368f06]. **Prompts** are user-selected query scaffolds, surfaced for explicit selection (e.g. slash commands), retrieved via `prompts/get` and completion-assisted on their `arguments` [cc324bc4a]. If the engine ever exposes itself over the HTTP transport, the Security Best Practices are mandatory, not optional: per-client consent before any third-party authorization flow to defeat the confused deputy, no token passthrough (validate that inbound tokens were issued to this server), and secure non-deterministic session IDs bound to user identity to defeat session hijacking [cf13e1cfc].
